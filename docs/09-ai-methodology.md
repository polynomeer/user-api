# 09. AI 활용 방법론

> 이 문서는 **어떻게** AI를 썼는지를 방법론 관점에서 정리한다. 시간순 진행 기록은 [08-process-log](08-process-log.md), 단계별 활용 내역은 [AI_USAGE](AI_USAGE.md)를 본다.

## 1. 전제와 목표

| 항목 | 내용 |
|---|---|
| 도구 | Claude Code (데스크톱 앱), 모델 Claude Opus 5.5. 서브에이전트 정의는 Sonnet(명세·테스트·제출 점검)과 Opus(코드 리뷰). 이번 세션에서는 도중에 정의한 에이전트를 이름으로 부를 수 없어 같은 지침을 범용 에이전트에 넘겨 실행 |
| 제약 | 문서 수령 후 90분 내 제출. 대면 인터뷰에서 **진행 과정까지 검증** |
| 목표 | 속도는 AI로 얻되, ① 모든 코드를 설명할 수 있고 ② 결과를 증거로 보여줄 수 있으며 ③ 의사결정 이력이 남는 것 |

이 목표에서 세 가지 원칙을 세웠다.

1. **사람이 결정하고 AI는 실행한다.** 가정 확정, 설계 변경, 커밋, 리뷰 반영 범위, 외부 발행(push)은 사람이 승인한다.
2. **AI의 산출물과 보고는 주장일 뿐 사실이 아니다.** 테스트·실행·바이트 확인 같은 독립된 증거로 확인한 것만 사실로 다룬다.
3. **모든 결정은 추적할 수 있어야 한다.** 판단 근거는 문서와 커밋 바디에, AI 개입은 `Co-Authored-By`와 AI_USAGE에 남긴다.

## 2. 구조: 명세 · 하네스 · 루프

AI를 그냥 대화 상대로 쓰지 않고, 세 층으로 감싸서 썼다.

```
┌──────────────────────────────────────────────────────────────┐
│ 명세 층 (무엇을)   docs/01~07, CLAUDE.md                        │
│   번호 붙은 요구사항(FR/NFR/A-x) → 이후 모든 지시·검증의 기준       │
├──────────────────────────────────────────────────────────────┤
│ 하네스 층 (어디까지) .claude/ 권한·훅·스킬·서브에이전트, git 훅     │
│   AI가 넘으면 안 되는 선을 프롬프트가 아니라 장치로 강제            │
├──────────────────────────────────────────────────────────────┤
│ 루프 층 (어떻게)   단계 루프: 테스트 → 구현 → 검증 → 승인 → 커밋    │
│   매 단계 같은 절차를 반복해 품질의 하한을 고정                     │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 명세 층: 문서를 AI의 작업 기억으로 쓰기

대화가 길어지면 AI의 맥락은 흐려지고 요약된다. 그래서 **결정은 대화가 아니라 파일에 남겼다.**

| 기법 | 방법 | 효과 |
|---|---|---|
| 명세 우선 | 코드 작성 전에 요구사항·작업계획·설계·데이터 분석·테스트 계획을 먼저 작성 (`d7a6ac9`) | 구현 중 범위가 흔들리지 않음. AI가 "알아서" 기능을 추가하는 것을 막음 |
| 번호 체계 | 요구사항 FR-1~8, NFR-1~4, 가정 A-1~A-10, 테스트 P/L/API/R/I-x | "FR-3 검증해줘"처럼 짧고 모호하지 않은 지시와 대조가 가능 |
| 데이터 먼저 분석 | 구현 전에 `user.txt`의 줄바꿈(CRLF), 마지막 행 개행 없음, 오류 행 3건을 실측 | 기대 결과(성공 37 / 실패 3)를 테스트 기준값으로 먼저 고정 |
| 가정 명시 | 명세에 없는 부분을 근거와 함께 표로 남김 (A-3 빈 필드 보정 안 함, A-8 파일 없어도 기동 등) | AI와 사람이 같은 전제를 공유. 리뷰어가 의도된 결정을 결함으로 오인하지 않음 |
| `CLAUDE.md` | 읽을 문서, 명령어, 규칙(현재 단계만, 설계와 다르면 먼저 말하기, `user.txt` 불변, 스타일) | 새 세션·서브에이전트도 같은 규칙으로 시작 |

### 2.2 하네스 층: 지시 대신 장치로 강제하기

"하지 마"라는 프롬프트는 잊히거나 무시될 수 있다. 꼭 지켜야 하는 규칙은 **실행 환경이 막도록** 했다.

| 장치 | 강제하는 것 | 실패 시 동작 |
|---|---|---|
| 권한 `deny: Edit/Write(user.txt)` | 테스트 데이터 원본 보호 | 도구 호출 자체가 거부됨 |
| 권한 `deny: git push --force`, `git add -f` | 이력 파괴, ignore된 과제 원본 커밋 방지 | 거부 |
| 권한 `allow: gradlew, curl, git 조회·커밋` | 반복 확인 프롬프트 제거 (시간 절약) | - |
| `commit-msg` 훅 | 커밋 바디 필수 섹션(변경 내용·이유·검증) | 커밋 거부 |
| `Stop` 훅 (`test-gate.sh`) | 프로덕션 코드(`src/main`, 빌드 설정)가 바뀐 상태로 테스트가 실패하면 작업을 끝낼 수 없음. 테스트만 추가한 TDD Red 단계는 허용 | 종료를 막고 실패 로그를 AI에 돌려줌 |
| `.gitignore` | 과제 원본 pdf/png를 공개 레포에서 제외 | 추적 안 됨 |
| `.gitattributes: user.txt -text` | git의 줄바꿈 변환으로 테스트 데이터가 바뀌는 것 방지 | - |

**역할을 나눈 서브에이전트.** 구현과 검증을 같은 맥락에서 하면 자기 결과에 관대해진다. 그래서 검증은 **별도 맥락의 읽기 전용 에이전트**에 맡겼다.

| 에이전트 | 질문 | 권한 |
|---|---|---|
| `spec-reviewer` | 명세(FR/NFR/설계)를 충족하는가? | 읽기 전용 |
| `test-planner` | 테스트 계획 대비 빠진 케이스는? | 읽기 전용 |
| `code-reviewer` | 코드 품질(버그·예외·동시성·스타일·가독성·DDD·테스트·보안)은? | 읽기 전용 |
| `submit-checker` | 제출 체크리스트를 실제로 통과하는가? | 읽기 전용 |

모든 에이전트가 **코드를 고치지 않고 `파일:라인` 근거와 함께 보고만** 하게 했다. 구현은 메인 세션에서만 해서, 모든 변경이 사람이 보는 한 흐름 안에 있도록 했다.

**절차를 고정한 스킬.** `/step N`(단계 루프)과 `/checklist`(제출 점검)로 매번 같은 순서를 밟게 했다.

### 2.3 루프 층: 단계마다 같은 절차 반복

작업 계획의 각 단계(파서, 로더, 조회 API, 재적재, 예외 처리, 테스트 보강)를 다음 루프로 진행했다.

```
① 범위 확인 ─ 작업계획의 해당 단계와 설계 문서 관련 절만 읽기
② 테스트 먼저 ─ 실패(Red)를 실제로 확인
③ 구현 ─ 테스트 통과(Green)
④ 명세 검증 ─ 별도 에이전트가 요구사항·설계와 대조 (보고만)
⑤ 실동작 확인 ─ jar를 띄워 curl로 완료 기준 실행
⑥ 기록 ─ 설계 변경 시 문서 갱신, AI_USAGE 행 채우기
⑦ 승인 ─ 변경 요약과 커밋 메시지 초안을 사람에게 보여주고 확인
⑧ 커밋 ─ 훅이 형식을 검사
⑨ 시간 점검 ─ 계획 대비 경과, 컷라인(Must/Should/Could) 판단
```

②의 Red 확인과 ⑤의 실동작 확인을 빼지 않은 것이 중요했다. "테스트가 통과한다"만으로는 테스트가 맞는지 알 수 없고, "테스트가 통과한다"와 "실제 앱이 동작한다"는 다른 주장이기 때문이다.

## 3. 검증 체계: 무엇이 무엇을 잡는가

AI 산출물의 오류는 종류가 다양해서 검증도 여러 층으로 겹쳐 두었다. 아래는 이 과제에서 **실제로 오류를 잡은** 사례다.

| 검증 수단 | 잡는 것 | 이 과제에서 실제로 잡은 것 |
|---|---|---|
| TDD Red 확인 | 테스트가 아무것도 검증하지 않는 경우 | 모든 단계에서 컴파일 실패 또는 단언 실패를 먼저 확인 |
| 테스트 기대값 재계산 | AI가 만든 테스트의 잘못된 기대값 | 마지막 페이지 첫 ID를 1034로 썼으나 1016·1031 누락을 반영하면 1033 |
| 단언 강화 | 조건이 일어나지 않아도 통과하는 테스트 | 동시성 테스트가 3건 상태만 관측돼도 통과 → 두 상태 모두 관측돼야 통과하도록 수정 |
| 뮤테이션 확인 | 테스트의 결함 검출력 | `findAll`이 스냅샷을 두 번 읽게 고의로 고장 → 3회 모두 실패 확인 후 원복 |
| 반복 실행 | 불안정한(flaky) 테스트 | 동시성 테스트 10회 반복 통과 |
| 테스트를 추가하며 경로 검증 | 검토에서 "충족"으로 본 경로의 숨은 버그 | 406 등 대체 예외 경로에 `code`가 전혀 붙지 않던 버그 (상위 클래스가 본문을 나중에 생성) |
| 실제 기동 + curl | 테스트 환경과 실제 환경의 차이 | `loadedAt` 직렬화 형식, 파일 없을 때 기동, 실패 후 데이터 유지 |
| 명세 검증 에이전트 | 요구사항 누락 | FR-3(파싱 로그)을 검증하는 테스트가 없음 |
| 코드 리뷰 에이전트 | 설계·정확성 결함 | 헤더 판별이 파일 전체에 적용돼 깨진 데이터 행이 조용히 사라짐, 패키지 순환 의존, 소스에 들어간 보이지 않는 BOM 문자 |
| 도구로 사실 확인 | 에이전트 보고의 진위 | BOM 지적은 `od`로 바이트(`357 273 277`) 확인, 순환 의존은 import 분석 스크립트로 전후 비교 |
| 문서와 실제 대조 | 문서와 동작의 불일치 | README 예시의 `type` 필드가 실제 응답에 없음 → 제거. README의 curl 명령을 그대로 실행 |

**원칙: 에이전트 보고를 그대로 옮기지 않는다.** 서브에이전트의 보고는 다른 모델의 출력이다. 핵심 지적은 직접 재현하거나 도구로 확인한 뒤 반영했고, 제안이 틀린 경우에는 따르지 않았다. 예를 들어 리뷰어는 `UserDataInitializer`를 `config`로 옮기자고 했지만, `service`가 이미 `config`에 의존해 새 순환이 생기므로 `startup`을 택했다.

## 4. 사람이 판단한 지점

AI가 초안과 선택지를 내고, 아래 결정은 사람이 내렸다.

| 지점 | 결정 내용 |
|---|---|
| 가정 확정 | A-1~A-10 (빈 필드 보정 여부, 중복 ID 처리, 파일 없을 때 기동 정책 등) |
| 단계별 커밋 | 매 단계 커밋 메시지 초안을 확인한 뒤 승인 |
| 하네스 수정 | `commit-msg` 훅 버그(`##` 제목까지 주석으로 지움) 수정은 사람의 승인 후 진행. AI가 자신을 감시하는 장치를 스스로 고치지 않도록 함 |
| 리뷰 반영 범위 | 코드 리뷰 지적 16건 중 #1·#5를 먼저, 이어서 #2·#3만 반영. 나머지는 "인터뷰에서 설명"으로 보류 |
| 설계 유지/변경 | `GET /reload`의 405화 제안 기각(`/abc` → 400 설계 유지) |
| 외부 발행 | push와 메일 발송은 사람이 결정·실행 |

**지금 할 가치 판단.** 90분 과제에서 모든 개선을 할 수는 없다. 코드 리뷰어가 지적마다 "제출 전 / 시간 남으면 / 인터뷰에서 설명만"을 표기하게 해서, 과설계 제안(ID·연봉 값 객체, 파라미터 객체 등)을 걸러내고 실제 결함만 고쳤다.

## 5. AI가 틀린 사례와 교정 방식

AI는 이 과제에서 여러 번 틀렸다. 숨기지 않고 유형별로 정리한다. 교정 방식이 곧 방법론의 근거다.

| 유형 | 사례 | 어떻게 발견했나 | 교정 |
|---|---|---|---|
| 계산 오류 | 테스트 기대값 1034 (정답 1033) | 테스트 작성 직후 재계산 | 기대값 수정 |
| 가독성 결함 | `switch` guard 안에 `Set.add` 부작용 | 구현 후 자체 검토 | 명시적 if/else |
| 잘못된 테스트 설계 | `GET /reload`에 405 기대 (실제 400) | 테스트 실패 원인 분석 | 설계상 올바른 동작으로 판단, 테스트 삭제 |
| 잘못된 테스트 설계 | MockMvc로 406 본문 검증 시도 | 테스트 실패 원인 분석 | HTTP상 본문 없는 406이 맞음 → 핸들러 직접 호출로 변경 |
| 실제 버그 | 대체 예외 경로에서 `code` 누락 | 위 테스트를 다시 쓰는 과정 | `super` 호출 후 본문 보정 |
| 과장된 주장 | 동시성 테스트가 "실제 겹침 보장" | 명세 검증 에이전트 | 표현 정정, 한계를 문서에 명시, 다음 커밋 바디에 정정 기록 |
| 도구 사용 실수 | zsh에서 `?` glob, `set -- $u` 미분리로 잘못된 curl | 결과가 비정상(Tomcat HTML 400) | 스크립트 수정 후 재실행. 앱 결함으로 보고하지 않음 |
| 자기가 만든 결함 | 소스에 보이지 않는 BOM 문자 삽입 | 코드 리뷰 에이전트 | `'﻿'` 이스케이프로 교체 |
| 상황 판단 오류 | 경과 시간을 실제보다 크게 보고 | 앱 로그의 실제 시각과 대조 | 정정해서 알림 |
| 부정확한 기록 | 커밋 바디에 "통합 테스트 미추적"이라 기록 (실제로는 사용자가 이미 커밋) | 커밋 후 `git status`·`git log` 확인 | push 전 자기 커밋만 `--amend`로 정정 |

공통된 교훈은 **"통과했다", "확인했다"는 AI의 진술을 그 자체로 믿지 않고, 그 진술을 뒷받침하는 출력(테스트 결과, 바이트, 로그 시각, git 상태)을 함께 보는 것**이다.

## 6. 추적성

| 대상 | 남기는 곳 |
|---|---|
| 무엇을 왜 바꿨나 | 커밋 바디의 변경 내용·변경 이유·설계 결정·검증 (모든 커밋, 훅으로 강제) |
| AI가 관여했나 | 커밋의 `Co-Authored-By`, [AI_USAGE](AI_USAGE.md)의 단계별 "AI가 한 일 / 본인이 한 일" |
| 결정의 근거와 대안 | [01-requirements](01-requirements.md) 가정, [07-tech-decisions](07-tech-decisions.md) |
| 진행 순서 | [08-process-log](08-process-log.md), `git log --reverse` |
| 정정 이력 | 틀린 주장을 정정할 때 이전 커밋을 고치지 않고 다음 커밋 바디에 정정 사실을 기록 (push 전 자기 마지막 커밋만 예외적으로 amend) |

## 7. 한계와 개선점

| 한계 | 영향 | 다음에는 |
|---|---|---|
| 하네스를 4단계 직전에 구성 | 초기 단계에는 훅·에이전트가 적용되지 않음 | 착수 전 템플릿으로 미리 준비 |
| 세션 도중 추가한 에이전트는 이름으로 호출 불가 | 같은 지침을 범용 에이전트에 넘겨 실행 | 세션 시작 전에 에이전트 정의 |
| `commit-msg` 훅의 정규식 버그 | 규칙을 지킨 메시지가 거부됨 | 훅도 통과·거부 케이스로 테스트 후 도입 |
| `.git/hooks`는 git이 추적하지 않음 | 새로 clone한 환경에는 훅이 없음 | `.githooks/` + `core.hooksPath`로 레포에 포함 |
| 사람과 AI가 같은 작업 트리에서 동시에 커밋 | AI의 미커밋 수정이 사람의 커밋에 섞임 | 동시 작업 시 브랜치나 worktree 분리 |
| 동시성 테스트가 "조회 도중 교체"를 직접 증명하지 못함 | 검출력의 한계 | 뮤테이션 확인으로 보완, 한계를 문서화 |
| 시간 추정 | AI의 경과 시간 보고가 부정확했음 | 실제 시각(로그·시계)을 기준으로 판단 |

## 8. 재사용할 수 있는 요약

1. **명세를 먼저 파일로 만들고 번호를 붙인다.** 이후 모든 지시와 검증이 그 번호를 기준으로 한다.
2. **지켜야 할 규칙은 프롬프트가 아니라 권한·훅으로 강제한다.**
3. **구현과 검증의 맥락을 분리한다.** 검증 에이전트는 읽기 전용, 근거(`파일:라인`) 필수.
4. **단계마다 같은 루프를 돈다.** Red 확인과 실동작 확인을 생략하지 않는다.
5. **AI의 진술은 증거로 확인한다.** 테스트 결과, 실행 출력, 바이트, git 상태.
6. **결정은 사람이 하고 기록은 남긴다.** 커밋 바디와 활용 내역에 이유와 정정까지.
