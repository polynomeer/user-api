## 0. 공통 판단 기준

모든 결정에 아래 기준을 우선순위대로 적용했다.

| 순위 | 기준 | 의미 |
|---|---|---|
| 1 | **요구사항 충족·정확성** | FR 전부 동작, 잘못된 데이터·요청에서도 일관된 동작 (NFR-1·2) |
| 2 | **데이터 일관성** | 재적재 중에도 부분 갱신 상태가 보이지 않음 (NFR-3) |

## 1. 언어·프레임워크·빌드

### 1.1 Java 21 (`record`, `sealed`)

- **선택**: Java 21 toolchain. 값 객체는 `record`, 결과 타입은 `sealed interface`
- **대안**: Java 17
- **기준**: 로컬 JDK(Corretto 21)가 LTS이며 Spring Boot 4가 지원. `record`로 DTO·도메인의 보일러플레이트 제거, `sealed`로 파싱 결과를 닫힌 타입으로 표현해 `switch` 패턴 매칭에서 누락을 컴파일러가 잡음
- **트레이드오프**: 구버전 JDK 환경에서는 실행 불가 → README에 JDK 21 명시
- **재검토 조건**: 배포 환경 JDK가 21 미만으로 고정된 경우

### 1.2 Spring Boot 4.1.1 + Spring MVC (`starter-webmvc`)

- **선택**: start.spring.io 기본 stable 버전, 서블릿 기반 MVC
- **대안**: WebFlux, Spring Boot 3.x
- **기준**:
  - 데이터가 메모리에 있어 I/O 대기가 없음 → 논블로킹의 이점이 없고 리액티브는 코드·테스트 복잡도만 증가
  - MVC는 MockMvc 테스트, Bean Validation 메서드 검증, `ProblemDetail`이 기본 제공되어 요구사항(에러 처리·검증)을 최소 코드로 충족
  - 최신 stable을 쓰되 프로젝트 생성기의 기본값을 따라 버전 선정 시간을 없앰
- **트레이드오프**: 매우 높은 동시 접속에서는 스레드 모델 한계 (이 과제 범위 밖)
- **재검토 조건**: 데이터 출처가 원격 API로 바뀌어 I/O 대기가 지배적일 때

### 1.3 Gradle (Groovy DSL, wrapper 포함)

- **선택**: Gradle wrapper 커밋
- **대안**: Maven, Kotlin DSL
- **기준**: 평가자가 별도 설치 없이 `./gradlew build` 한 줄로 빌드·테스트. 생성기 기본값 그대로 사용해 설정 시간 최소화
- **트레이드오프**: Kotlin DSL 대비 IDE 타입 지원이 약함 (빌드 스크립트가 짧아 영향 미미)

### 1.4 Lombok 미사용

- **선택**: `record` + 명시적 생성자 주입
- **대안**: Lombok(`@Getter`, `@RequiredArgsConstructor`, `@Slf4j`)
- **기준**: `record`가 Lombok의 주 용도(값 객체)를 대체. 어노테이션 프로세서 설정이 없어 빌드가 단순하고, 생성되는 코드가 보이지 않는 문제(설명 가능성)를 피함
- **트레이드오프**: 서비스·컨트롤러 생성자와 Logger 선언을 직접 작성 (클래스 수가 적어 비용 작음)

## 2. 저장소와 동시성

### 2.1 인메모리 불변 스냅샷 + `AtomicReference`

- **선택**: 한 번의 적재 결과를 불변 `UserSnapshot`(정렬 목록, ID 맵, 실패 목록, 적재 시각)으로 만들고 `AtomicReference.set()`으로 통째 교체
- **대안**

| 대안 | 기각 이유 |
|---|---|
| `ConcurrentHashMap`에 직접 put/remove | 재적재 도중 조회하면 일부만 갱신된 상태가 보임 → NFR-3 위반. 목록·실패 목록과의 정합성도 깨짐 |
| `ReadWriteLock`으로 보호되는 가변 컬렉션 | 정합성은 지키지만 모든 조회가 락을 거침. 락 범위 실수 위험 |
| H2 + JPA | 과제가 힙 메모리 적재를 허용. 37건 데이터에 스키마·엔티티·트랜잭션은 과잉. 설명할 코드만 증가 |

- **기준**: 조회는 락 없이 `snapshot.get()` 한 번만 읽고 그 스냅샷으로 끝까지 처리 → 목록의 `content`와 `totalElements`가 서로 다른 버전에서 나오는 일이 없음. 불변 컬렉션(`List.copyOf`, `Map.copyOf`)이라 공유해도 안전
- **트레이드오프**: 교체 순간 신·구 스냅샷이 동시에 메모리에 존재(일시적으로 2배). 데이터가 작아 무시 가능
- **재검토 조건**: 데이터가 힙에 담기 어려운 규모이거나, 다중 인스턴스 간 데이터 공유가 필요할 때 (→ 03-design 8.3)

### 2.2 재적재 직렬화: `synchronized`

- **선택**: `UserService.reload()`에 `synchronized`
- **대안**: `ReentrantLock.tryLock()`으로 진행 중 요청을 409로 거절, 무락(lock-free) 허용
- **기준**: 동시 재적재 시 파일을 중복으로 읽거나 늦게 시작한 적재가 먼저 끝나 덮어쓰는 순서 역전을 막음. 조회는 이 락과 무관하므로 조회 성능 영향 없음. 가장 짧고 읽기 쉬운 코드
- **트레이드오프**: 동시 요청은 대기 후 각각 재적재를 수행(중복 작업). 재적재가 드물고 빠르므로 허용
- **재검토 조건**: 파일이 커서 재적재가 오래 걸리거나 외부 노출로 남용 가능성이 있을 때 → `tryLock` + 409

## 3. 파싱·적재

### 3.1 파서는 스프링 비의존 순수 클래스 + `ParseResult` 반환

- **선택**: `UserLineParser`가 한 줄을 받아 `ParseResult.Success | Failure`를 반환. 예외를 흐름 제어에 쓰지 않음
- **대안**: 실패 시 커스텀 예외를 던지고 로더에서 catch
- **기준**:
  - 잘못된 행은 **예상된 입력**(샘플에 3건 존재)이지 예외 상황이 아님 → 값으로 표현하는 것이 의미상 맞음
  - 한 행의 실패가 전체 적재를 중단시키지 않음 (FR 요구)
  - 스프링 없이 단위 테스트 가능 → 경계값 테스트가 빠르고 많음
  - `sealed`라 처리 누락을 컴파일 단계에서 발견
- **트레이드오프**: 호출부에서 결과 분기 필요 (패턴 매칭으로 짧게 처리)

### 3.2 검증 정책: 엄격 검증, 자동 보정 없음

- **선택**: 필드 수 정확히 5개, 필드별 규칙 위반 시 실패 처리. 에러 코드 enum(`ParseErrorCode`)으로 원인 분류
- **대안**: 빈 필드·오타를 추정 보정(예: `O`→`0`)
- **기준**: 데이터를 임의로 고치면 오류가 은폐되고 잘못된 값이 정상 데이터처럼 노출됨. 실패를 기록·조회 가능하게 해 운영자가 원본을 고치도록 하는 것이 안전 (A-3)
- **세부 결정**

| 항목 | 결정 | 근거 |
|---|---|---|
| 앞뒤 공백 | trim | 샘플이 `1001 , 김다나 , ...` 형식 (A-1) |
| 연봉 `_` | 자릿수 구분자로 허용, 3자리 그룹 형식만 | 전 데이터가 이 형식. Java 숫자 리터럴과 같은 의미 (A-2) |
| 성별 | `M`/`F`만 | 샘플 기준 (A-4) |
| 나이 | 0~150 | 명백히 비현실적인 값 차단 |
| ID 중복 | 먼저 나온 행 유지, 이후 행 `DUPLICATE_ID` 실패 | 조용한 덮어쓰기보다 명시적 실패 (A-5) |
| 빈 줄·헤더·구분선 | 실패가 아닌 skip | 데이터가 아닌 서식 행 (A-6) |
| 숫자 범위 | int 초과 시 실패 | `NumberFormatException`을 잡아 Failure로 변환 |

### 3.3 파일 읽기: `BufferedReader` 줄 단위, UTF-8

- **선택**: `Files.newBufferedReader(path, UTF_8)`로 한 줄씩 처리
- **대안**: `Files.readAllLines`, `Files.lines` 스트림
- **기준**: `readLine()`이 CRLF·LF를 모두 처리하고 마지막 행 개행 없음도 정상 처리 (04-data-analysis 확인 사항). 줄 번호를 세며 실패 위치를 기록하기 쉬움. 전체를 한 번에 올리지 않아 파일이 커져도 원본 텍스트를 통째로 보관하지 않음
- **오류 처리**: 파일 없음·권한 없음·UTF-8 아님(`MalformedInputException`)은 `DataLoadException`으로 변환 → 스냅샷을 교체하지 않음 (NFR-2, A-7)

### 3.4 기동 시 적재 실패 정책: 빈 데이터로 기동

- **선택**: `ApplicationRunner`에서 적재, 실패 시 ERROR 로그 후 빈 데이터로 기동 (A-8)
- **대안**: fail-fast (기동 실패로 종료)
- **기준**: 파일 문제는 파일만 고치면 재적재 API로 복구 가능 → 프로세스를 죽이는 것보다 가용성이 높음. 재적재 API가 있다는 요구사항과 일관됨
- **트레이드오프**: 빈 데이터 상태가 조용히 서비스될 위험 → ERROR 로그로 알리고, 운영 환경에서는 헬스체크에 적재 상태를 넣어 보완 (03-design 8.3)
- **적용 범위**: 빈 데이터로 계속 진행하는 것은 `DataLoadException`(파일을 읽을 수 없음)만이다. 파서 버그 같은 다른 `RuntimeException`이나 잘못된 `file-path` 설정은 잡지 않아 기동이 실패한다. 파일 문제는 운영 중 복구할 수 있지만, 코드·설정 오류는 재적재로 고쳐지지 않으므로 빈 데이터로 덮으면 문제만 숨기게 된다 (03-design 6.1)
- **재검토 조건**: 데이터 없이는 서비스 의미가 없는 환경 → fail-fast로 전환하고 오케스트레이터 재시작에 맡김

### 3.5 재적재 결과 검증: 읽을 수 있으면 그대로 교체 (0건 포함)

- **선택**: 파일을 끝까지 읽기만 하면 결과가 0건이거나 일부여도 스냅샷을 교체하고 200을 반환
- **대안**: (a) 성공 0건이면 교체를 거부하고 에러(`EMPTY_DATA`) 반환, (b) 이전 대비 건수가 급감하면 거부, (c) 파일 수정 시각·크기가 읽는 동안 바뀌었으면 거부
- **기준**:
  - "0건"이나 "건수 감소"가 정상 데이터일 수 있어, 거부 기준은 요구사항 근거 없이 정책을 지어내는 일이 됨
  - 재적재 응답에 `successCount`·`failureCount`가 있어 호출자가 결과를 바로 확인할 수 있음
  - 쓰는 중인 파일 문제는 읽는 쪽보다 쓰는 쪽 규약(임시 파일에 쓴 뒤 rename으로 원자적 교체)으로 막는 것이 정석
- **트레이드오프**: 실수로 비운 파일을 재적재하면 데이터가 사라짐. 원본 파일을 고친 뒤 다시 재적재하면 복구됨
- **재검토 조건**: 파일을 외부 시스템이 자동으로 갱신하거나 재적재를 자동화할 때 → (a) 가드부터 추가

## 4. API 설계

### 4.1 페이징: 직접 구현한 `PageResult` (구 `PageResponse`)

- **선택**: 0 기반 page, 기본 size 10, 최대 100, ID 오름차순. 범위를 넘는 page는 에러가 아닌 빈 `content` (A-9, A-10)
- **대안**: Spring Data `Pageable`/`Page`, 커서 기반 페이징
- **기준**:
  - Spring Data는 JPA 등 데이터 모듈 의존을 끌어옴. 인메모리 리스트에는 `subList` 몇 줄이면 충분
  - 응답 형태(`content`, `page`, `size`, `totalElements`, `totalPages`)는 Spring Data 관례를 따라 사용자에게 익숙하게
  - ID 정렬로 같은 요청이 항상 같은 결과 (결정적)
  - `page * size`는 `long`으로 계산해 int 오버플로 방지
- **트레이드오프**: 커서 방식이 아니라 재적재 사이에 페이지를 넘기면 항목이 밀릴 수 있음 (데이터가 드물게 바뀌어 허용)

### 4.2 이름 검색: 부분 일치 선형 탐색

- **선택**: 스냅샷 목록을 `String.contains`로 필터 후 페이징
- **대안**: 이름 인덱스(n-gram 맵), 정확 일치만 지원
- **기준**: 37건에 대한 O(n) 탐색은 측정할 필요도 없이 빠름. 인덱스는 재적재마다 재구축 비용과 코드만 늘림. 부분 일치가 사용자 기대(성씨로 검색 등)에 맞음
- **재검토 조건**: 데이터가 수만 건 이상이고 검색 빈도가 높을 때 → 스냅샷 생성 시 인덱스를 함께 구축

### 4.3 경로 설계

- `/api/users/search`, `/api/users/parse-failures`는 리터럴 경로라 `/{id}`보다 우선 매칭
- `{id}`를 `int`로 바인딩해 숫자가 아니면 스프링이 400으로 처리 → 별도 검증 코드 불필요
- 재적재는 상태를 바꾸므로 `POST` (멱등이 아닌 부수효과 동작)

### 4.4 요청 검증: Bean Validation 메서드 파라미터 검증

- **선택**: 컨트롤러 파라미터에 `@Min`, `@Max`, `@NotBlank` 선언. 한글 메시지를 제약에 직접 정의
- **대안**: 컨트롤러·서비스에서 `if` 수동 검증
- **기준**: Spring 6.1+ 내장 메서드 검증(`HandlerMethodValidationException`)으로 클래스 수준 `@Validated` 없이 동작. 제약이 시그니처에 보여 API 계약이 코드에서 바로 읽힘

### 4.5 에러 응답: RFC 9457 `ProblemDetail` + `code` 확장 필드

- **선택**: `GlobalExceptionHandler`가 `ResponseEntityExceptionHandler`를 상속. 모든 에러를 `ProblemDetail` 형식으로 통일하고 기계 판독용 `code`(`USER_NOT_FOUND`, `INVALID_PARAMETER`, `DATA_LOAD_FAILED` 등)를 추가
- **대안**: 자체 에러 DTO(`{code, message}`)
- **기준**:
  - 표준 형식이라 클라이언트가 별도 계약 없이 해석 가능, Spring 내장 지원
  - 상속으로 스프링 표준 예외(405, 415 등)의 상태 코드 결정을 프레임워크에 맡기고 한글 `detail`과 `code`만 채움 → 누락된 예외 처리가 생기지 않음 (NFR-1)
  - 500은 내부 메시지를 노출하지 않고 스택트레이스는 서버 로그에만
- **위치**: 핸들러는 HTTP 경계인 `api.error`, 예외 타입은 웹 의존이 없는 `exception` 패키지. 로더(인프라)가 던지는 예외가 웹 계층 클래스와 같은 패키지에 섞이지 않도록 분리
- **`DATA_LOAD_FAILED`를 503이 아닌 500으로**: 원인(파일 없음·권한·인코딩)은 서버 측 설정 문제이고 재시도로 풀린다는 보장이 없다. 503은 "일시적, 재시도 가능"을 뜻해 맞지 않음. 재검토 조건: 재적재를 비동기·잠금 방식으로 바꿔 "진행 중"을 거절하게 되면 그 경우는 409/503으로 구분
- **트레이드오프**: 응답 필드가 자체 DTO보다 많음

## 5. 설정·로깅

### 5.1 `@ConfigurationProperties` + 환경변수 재정의

- **선택**: `user-api.data.file-path`(기본 `./user.txt`)를 `UserDataProperties`로 바인딩
- **대안**: 경로 하드코딩, `@Value`
- **기준**: 실행 위치·환경마다 경로가 다름 → `USER_API_DATA_FILE_PATH` 환경변수로 코드 수정 없이 변경. 테스트에서 `@TempDir` 경로를 주입하기 쉬움. 관련 설정을 타입으로 묶어 오타를 컴파일 단계에서 방지

### 5.2 로깅: SLF4J, 한글 메시지, 행 단위 WARN

- **선택**: 파싱 실패마다 WARN (`line`, `code`, `raw`, `reason`), 적재 완료 시 INFO 요약(`success`, `failure`), 파일 오류는 ERROR + cause
- **기준**: 요구사항(파싱 실패 로그)을 충족하면서, 운영자가 로그 한 줄로 원본 파일의 몇 번째 줄을 어떻게 고칠지 알 수 있게 함. 로그 레벨로 심각도를 구분해 경보 기준을 세우기 쉬움
- **재검토 조건**: 로그 수집 시스템이 있는 환경 → JSON 구조화 로그

## 6. 테스트

| 선택 | 기준 |
|---|---|
| JUnit 5 + AssertJ | 스프링 기본 포함, 읽기 쉬운 단언 |
| 파서 순수 단위 테스트 (TDD) | 가장 규칙이 많은 곳. 정상 행·오류 3종·경계값(int 초과, `+1`, 공백)을 스프링 없이 빠르게 검증 |
| `@TempDir` 복사본으로 로더·재적재 테스트 | 원본 `user.txt`를 절대 수정하지 않음. 파일 없음·수정·이름 변경 시나리오를 격리 재현 |
| MockMvc 컨트롤러 테스트 | 실제 서버 없이 HTTP 상태 코드·에러 형식(400/404/405/500)을 계약 수준에서 검증 |
| 동시성 테스트 | 재적재와 조회를 동시에 실행해 부분 갱신 상태가 보이지 않음(NFR-3)을 증명 |
| JaCoCo 리포트 | 커버리지 수치를 근거로 테스트 누락 구간 확인 (`build/reports/jacoco`) |
