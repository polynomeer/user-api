# 11. 프론트엔드 설계

> 과제 API 5종을 브라우저에서 바로 확인할 수 있는 단일 페이지입니다. 별도 빌드 도구 없이 스프링 부트 정적 리소스로 함께 배포합니다.
> API 명세는 [`03-design.md` 5절](03-design.md), 기술 선택 근거는 [`07-tech-decisions.md` 4.6](07-tech-decisions.md)을 따릅니다.

## 1. 목표와 범위

| 구분 | 내용 |
|---|---|
| 목표 | 목록·검색·단건 조회·파싱 실패 조회·재적재를 화면에서 수행하고, 에러 응답(`code`, `detail`)을 그대로 보여 줌 |
| 사용자 | 과제 평가자, 데이터 파일을 고치고 재적재하는 운영자 |
| 하지 않는 것 | 인증, 사용자 데이터 편집, 경로 기반 라우팅(화면은 `/` 하나, 상태는 쿼리로만 표현), 빌드 도구·프레임워크, 다국어 |

## 2. 구조

```
src/main/resources/static/
├── index.html   # 마크업. 외부 리소스 없음
├── app.css      # 스타일 (라이트/다크 대응)
└── app.js       # API 호출, 상태, 렌더링 (ES 모듈 1개)
```

- 스프링 부트가 `static/index.html`을 `/`에서 자동으로 제공합니다 (welcome page). 컨트롤러 추가가 필요 없습니다
- API와 **같은 출처**에서 제공되므로 CORS 설정이 필요 없습니다
- `./gradlew bootRun` 후 `http://localhost:8080/`로 접속합니다. jar 하나로 API와 화면이 함께 배포됩니다

## 3. 화면 구성

```
┌────────────────────────────────────────────────────────────┐
│ 사용자 데이터 콘솔        적재 시각 2026-10-13 10:30  [재적재] │  ← 헤더 + 적재 상태
├────────────────────────────────────────────────────────────┤
│ [알림] 재적재 완료: 성공 37건, 실패 3건                       │  ← 알림 영역 (aria-live)
├────────────────────────────────────────────────────────────┤
│ [사용자]  [파싱 실패 3]                                      │  ← 탭
├────────────────────────────────────────────────────────────┤
│ 이름 [______] [검색] [초기화]     ID [____] [조회]            │
│ ┌──────┬────────┬────┬────┬─────────────┐  ┌────────────┐  │
│ │ ID   │ 이름   │나이│성별│ 연봉        │  │ 상세       │  │
│ │ 1001 │ 김다나 │ 23 │ M  │ 30,000,000  │  │ ID 1001    │  │
│ │ ...  │        │    │    │             │  │ ...        │  │
│ └──────┴────────┴────┴────┴─────────────┘  └────────────┘  │
│ [이전] 1 / 4 페이지 (총 37건) [다음]   페이지 크기 [10 ▾]     │
└────────────────────────────────────────────────────────────┘
```

| 영역 | 동작 | 사용 API |
|---|---|---|
| 적재 상태 | 마지막 적재 시각 표시. `loadedAt`이 `null`이면 "데이터가 적재되지 않았습니다" 경고 | `GET /api/users/parse-failures` |
| 재적재 버튼 | 재적재 후 결과 건수를 알림으로 표시하고 현재 탭을 다시 조회 | `POST /api/users/reload` |
| 사용자 목록 | ID 오름차순 테이블, 이전/다음 페이지, 페이지 크기 10·20·50·100 | `GET /api/users?page&size` |
| 이름 검색 | 검색어가 있으면 검색 결과를 같은 테이블·페이징으로 표시. 초기화하면 전체 목록으로 | `GET /api/users/search?name&page&size` |
| ID 조회 / 행 선택 | 상세 패널에 단건 조회 결과 표시 | `GET /api/users/{id}` |
| 파싱 실패 탭 | 행 번호·에러 코드·사유·원본 행 테이블. 탭 제목에 건수 표시 | `GET /api/users/parse-failures` |

## 4. 상태와 흐름

화면 상태는 `app.js`의 객체 하나로 관리합니다. 서버 데이터는 캐시하지 않고 필요할 때 다시 조회합니다 (데이터가 작고, 재적재로 언제든 바뀌기 때문).

```js
const state = { tab: 'users', keyword: '', page: 0, size: 10 };
```

| 이벤트 | 상태 변화 | 후속 조회 |
|---|---|---|
| 페이지 로드 | URL 쿼리에서 읽음 (4.1) | 현재 탭 + 적재 상태 |
| 뒤로/앞으로 가기 | URL 쿼리에서 다시 읽음 | 현재 탭 |
| 검색 | `keyword` 설정, `page = 0` | 검색 |
| 초기화 | `keyword = ''`, `page = 0` | 목록 |
| 이전/다음 | `page ± 1` | 목록 또는 검색 |
| 페이지 크기 변경 | `size` 변경, `page = 0` | 목록 또는 검색 |
| 탭 전환 | `tab` 변경, 알림 지움 | 해당 탭 조회 |
| 재적재 성공 | 변화 없음 | 적재 상태 + 현재 탭 다시 조회 |

- **재적재로 페이지가 범위를 벗어나는 경우**: 서버는 범위 밖 페이지에 빈 `content`를 돌려줍니다 (A-9). 화면은 `content`가 비어 있고 `page > 0`이고 `totalPages > 0`이면 마지막 페이지(`totalPages - 1`)로 한 번 다시 조회합니다
- **늦게 도착한 응답**: 빠르게 페이지를 넘기면 이전 요청의 응답이 나중에 도착할 수 있습니다. 요청마다 순번을 붙이고 최신 순번의 응답만 반영합니다
- **재적재 중복 클릭**: 요청이 끝날 때까지 버튼을 비활성화합니다. 서버도 `synchronized`로 직렬화하지만 불필요한 중복 요청을 줄입니다

### 4.1 URL 상태 동기화

화면 상태를 쿼리에 남겨 **새로고침, 뒤로 가기, 링크 공유** 후에도 같은 화면을 보여 줍니다.

| 쿼리 | 상태 | 기본값 (URL에서 생략) | 허용 값 |
|---|---|---|---|
| `tab` | 탭 | `users` | `users`, `failures` |
| `name` | 검색어 | 없음 | 앞뒤 공백 제거 후 비어 있지 않은 문자열 |
| `page` | 페이지 | `0` | 0 이상 int 범위 정수. **API와 같은 0부터 시작하는 번호**라 화면 URL과 API 호출이 1:1로 대응 (`/?page=2` ↔ `/api/users?page=2`). 화면 표시는 1부터 (`3 / 4 페이지`) |
| `size` | 페이지 크기 | `10` | `10`, `20`, `50`, `100` |

- **기록 방식**: 사용자 조작(검색, 초기화, 이전/다음, 크기 변경, 탭 전환)은 `history.pushState`로 기록해 뒤로 가기 대상이 됩니다. 보정은 `replaceState`로 현재 항목을 덮어씁니다
- **잘못된 값 보정**: 허용 값이 아니면 기본값으로 바꾸고 URL도 보정합니다 (`/?page=-1&size=7&tab=zzz` → `/`). 서버에 잘못된 값을 보내 400을 받는 대신 화면에서 걸러냅니다. int 범위를 넘는 `page`도 여기서 걸러 서버 400(`INVALID_PARAMETER`)이 나지 않게 합니다
- **범위 밖 페이지**: URL의 `page`가 데이터보다 크면 재적재 후와 같은 규칙으로 마지막 페이지로 옮기고 URL을 보정합니다 (`/?page=99&size=50` → `/?size=50`)
- 기본값인 항목은 URL에서 빼서 첫 화면 주소가 `/`로 유지됩니다

## 5. 에러 처리

모든 호출은 `api(path, options)` 함수 하나를 거칩니다.

| 상황 | 판정 | 화면 표시 |
|---|---|---|
| 정상 | `response.ok` | 결과 렌더링 |
| API 에러 | 응답이 `application/problem+json` | 알림에 `detail`과 `code` 표시 (예: `ID 9999에 해당하는 사용자가 없습니다. (USER_NOT_FOUND)`) |
| 그 밖의 HTTP 에러 | `ok`가 아니고 본문이 ProblemDetail이 아님 | `요청을 처리할 수 없습니다 (HTTP 502)` |
| 네트워크 오류 | `fetch`가 예외 | `서버에 연결할 수 없습니다.` |

- 서버의 한글 `detail`을 그대로 보여 주므로 화면에 에러 문구를 중복 정의하지 않습니다. 서버가 에러 메시지의 단일 출처입니다
- 단건 조회 404는 상세 패널에 "사용자를 찾을 수 없습니다"로 표시하고, 알림에도 서버 `detail`을 띄웁니다
- 재적재 실패(500 `DATA_LOAD_FAILED`)는 서버 문구("기존 데이터를 유지합니다")를 그대로 보여 주고, 화면의 기존 데이터도 그대로 둡니다
- ID 입력은 `<input type="number" min="1">`로 1차 제한하지만, 검증의 기준은 서버입니다. 서버 400 응답도 같은 방식으로 표시합니다

## 6. 보안

- **데이터는 항상 `textContent`로 렌더링하고 `innerHTML`을 쓰지 않습니다.** 파싱 실패의 `rawLine`은 데이터 파일 원문이라 `<script>` 같은 문자열이 들어 있을 수 있습니다
- `index.html`에 CSP를 둡니다: `default-src 'self'`. 외부 스크립트·스타일·폰트를 쓰지 않으므로 같은 출처만 허용합니다
- 재적재 API에는 인증이 없습니다. 현재 범위 밖이며, 운영 시 `/admin` 분리와 인증이 필요합니다 (03-design 8.3)

## 7. 표현 규칙

| 항목 | 규칙 |
|---|---|
| 연봉 | `Intl.NumberFormat('ko-KR')`로 천 단위 구분 (`30,000,000`) |
| 적재 시각 | 서버 `Instant`(UTC)를 브라우저 지역 시각으로 `yyyy-MM-dd HH:mm:ss` 표시 |
| 빈 결과 | 테이블 자리에 "결과가 없습니다" |
| 로딩 | 요청 중 테이블에 `aria-busy="true"`, 버튼 비활성화 |
| 접근성 | 표는 `<table>`·`<th scope>`, 입력에 `<label>`, 알림은 `aria-live="polite"`, 탭은 `role="tab"` + `aria-selected` |
| 반응형 | 폭 768px 미만에서는 상세 패널을 표 아래로 내림 |

### 8.1 확인 결과 (2026-10-13)

F-1~F-16을 내장 브라우저에서 모두 확인했습니다 (F-13~F-16은 URL 상태 동기화 추가 후, 원본 `user.txt`를 읽기 전용으로 사용해 콘솔 에러 없음). 데이터 파일은 원본이 아닌 스크래치 디렉터리의 복사본·합성 파일을 `USER_API_DATA_FILE_PATH`로 지정해 사용했습니다. 콘솔 에러는 F-5(404)·F-8(500)의 의도된 응답뿐이고, CSP 위반은 없었습니다.

확인 중 발견해 고친 문제:

| 문제 | 원인 | 수정 |
|---|---|---|
| 선택 전에도 상세 패널에 필드 이름(ID, 이름…)이 보임 | `.detail dl { display: grid }`가 `hidden` 속성의 기본 `display: none`을 덮어씀 | `[hidden] { display: none !important }` 전역 규칙 추가 |
| 404 알림이 탭을 바꿔도 남아 있음 | 알림 해제 시점 누락 | 탭 전환 시 알림 지움 |
