# 06. 커밋 규칙

> 원칙: **모든 커밋은 한글로, 바디까지 상세히 작성한다.** 인터뷰에서 커밋 이력만으로 "무엇을, 왜, 어떻게 검증했는지" 재구성할 수 있어야 한다.

## 1. 형식

```
<type>: <한글 제목, 50자 이내, 마침표 없음, 명사형/동사형 종결>

## 변경 내용
- 무엇을 바꿨는지 (파일/클래스 단위가 아닌 동작 단위로)

## 변경 이유
- 왜 필요한지, 어떤 요구사항(FR-x/NFR-x)과 연결되는지

## 설계 결정
- 고려한 대안과 선택 이유 (해당 없으면 생략 가능)

## 검증
- 실행한 테스트/명령과 결과 (예: ./gradlew test 통과, curl 응답 확인)

Co-Authored-By: ...   (AI가 작성에 참여한 경우)
```

- 제목과 바디 사이 빈 줄 1개, 바디는 72자 내외에서 줄바꿈
- `변경 내용`, `변경 이유`, `검증`은 **필수**. `설계 결정`은 선택지가 있었던 경우 필수
- 커밋 템플릿: 레포 루트 `.gitmessage` (`git config commit.template .gitmessage` 적용됨)

## 2. type

| type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드·설정·의존성 등 기타 |

## 3. 커밋 단위

- 하나의 커밋 = 하나의 논리적 변경. 빌드·테스트가 통과하는 상태에서만 커밋
- 작업 계획서의 단계별 커밋을 기본으로 하되, 중간에 결정이 바뀌면 별도 커밋으로 남긴다
- 코드와 그 테스트는 같은 커밋에 포함 가능

## 4. 예시

```
feat: user.txt 행 파서 구현

## 변경 내용
- 한 줄을 User 또는 ParseFailure로 변환하는 UserLineParser 추가
- 필드 수, ID/나이/성별/이름/연봉 검증과 에러 코드(ParseErrorCode) 정의
- 연봉의 자릿수 구분자 '_'를 허용하고 제거 후 int로 변환

## 변경 이유
- FR-2(파일 → User 변환), FR-3/FR-7(파싱 실패 기록)의 기반 로직
- 샘플 데이터에 영문 O(1016), 빈 필드(1031), AAA(1039) 오류가 존재

## 설계 결정
- 예외 대신 ParseResult(Success/Failure)를 반환: 한 줄 실패가 전체 적재를
  중단시키지 않고, 실패 사유를 데이터로 수집하기 위함
- 빈 필드(,,)를 자동 보정하지 않고 실패 처리: 데이터 임의 보정은 오류를 숨김
- 스프링 비의존 순수 클래스로 두어 단위 테스트를 빠르게 유지

## 검증
- UserLineParserTest 12개 케이스 통과 (./gradlew test)
```
